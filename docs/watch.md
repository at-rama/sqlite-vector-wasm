# Upstream planning

Watch discovers official upstream releases and presents eligible SQLite × SQLite-Vector pairs for human selection. Discovery and forecasts do not establish build compatibility or publication acceptance.

## Official discovery

SQLite identities come from the complete [Fossil tag inventory](https://sqlite.org/src/taglist), with exact version-tag dates checked against their [official release pages](https://sqlite.org/chronology.html). The moving `release` tag is not a release version. SQLite-Vector identities come from all pages of its [published GitHub Releases](https://github.com/sqliteai/sqlite-vector/releases), preserving alpha/beta/rc suffixes and checking exact release IDs, official tag objects and their resolved commit identities. The released source archive is identified by that commit; Watch does not download it or demand an upstream-published archive checksum. Preparation establishes the source checksum under the existing acquisition policy. Drafts and unpublished snapshots supply no eligible release.

Ordinary discovery begins at SQLite `3.53.4` and SQLite-Vector `1.1.0`, using the shared upstream comparator. Thus `1.1.0-alpha.1` is below the SQLite-Vector bound, while `1.1.3-alpha.1` is above it. The Vector floor is fixed and inclusive: advancing a source pin does not recompute a predecessor. It is distinct from a published component reference, creates no fictitious publication and guarantees neither a nonempty plan nor email. Eligible `1.1.0` and `1.1.2` may both appear. These limits do not restrict manual Updates selection or rollback.

Discovery reads metadata only; it never downloads sources, changes pins or qualifies a candidate. Unreadable, incomplete, ambiguous or contradictory publication evidence fails planning. A purported SQLite prerelease lacking an admissible full-source publication identity is an explicit A-inputs dependency diagnostic, rather than a fabricated stable-only inventory. Current acquisition may require an established SQLite pin when its historical digest has disappeared from current download metadata; discovery does not invent a digest or an acquisition fallback.

Captured official metadata and synthetic failure cases are described in the [discovery fixtures](../tools/watch/tests/fixtures/README.md). Their tests exercise readers; they are not production qualification evidence.

## Publications and existing candidates

Watch consumes the shared publication reader, including exact payload checks for channel HEADs. It also reads historical `publication.json` provenance, corresponding distribution tags and npm identities. An already published pair remains excluded in its corresponding channel after a rollback or packaging correction. Partial occupied identities are retained by the shared calculation but are not invented as completed publications. Contradictory provenance and unavailable required pages fail the plan.

Queued or active Updates runs expose exact selections in their run names. Watch checks workflow, event, repository, main branch, run identity and attempt. The current title is `candidate sqlite=<version> SQLite-Vector=<version>`. Clearly identified sqlite-vec preparations remain historical; unknown or mixed relevant records fail rather than imply no preparation.

Open candidate PRs are inspected at their exact head commit. Only a newly introduced or modified `inputs/release.json`, with schema 2, validated against that head's `inputs/sqlite-vector.sources.lock.json` versions and preparation identity, establishes a candidate. An inherited descriptor in an unrelated PR does not. A matching run and PR are joined by preparation run and branch attempt; genuinely distinct PRs and attempts remain visible. Closed PRs and completed failed runs create no refusal history. A candidate's presence is observation, not qualification or a recommendation to merge.

## Reading a plan and choosing work

The Summary identifies the result first, then centralizes forecasts in **Forecast**, followed by every eligible unpublished pair in short blocks grouped by `latest` and `next` in their existing version order. The final **Reference state** section retains the published channel versions, exact upstream compositions and revisions, any partial occupied identities, and the invocation/observation context. SQLite comparisons use the target channel HEAD or `latest`. Vector comparisons use that channel’s Vector composition, otherwise `latest` if it contains Vector, otherwise no numerical Vector reference. An engine transition supplies progression when there is no Vector reference; applicable SQLite comparisons still prohibit regression. With comparable references, neither component regresses and at least one progresses. Experimental pairs also cannot fall behind `latest` on comparable components. Historical sqlite-vec references retain their real labels and numbering role; their versions are never ordered against Vector versions. A more advanced experimental HEAD does not block stable maintenance. All eligible alpha combinations remain visible; there is no newest-only selection.

Each entry contains exact upstream versions, Updates parameters and current preparation/PR links. Its channel section and the central Forecast section identify its forecast channel/increment/version without repeating it in the pair block. A common forecast is shown once for the channel. When forecasts differ within a channel, upstream selectors identify which pairs each applies to: SQLite alone when sufficient, otherwise the full SQLite × SQLite-Vector pair. The first pair is not a priority recommendation or a forecast for all other pairs. Forecasts call the same calculation as preparation against one publication snapshot, independently for each job. Several entries may predict the same number; none reserves it or assumes sequential adoption. These are alternatives at the observed published state, not a publication sequence. Later publication recalculates under its own gates; progression in either channel can change the remaining forecasts. Unselected eligible jobs recur naturally; reference progression can remove them without a refusal record. Missing stable bootstrap state or a calculation collision is an explicit failure.

The shared instructions above the entries link to the separate [Updates workflow](https://github.com/at-rama/sqlite-vector-wasm/actions/workflows/updates.yml). Choose zero, one or several jobs and open Updates only when you decide to prepare a pair. Each block gives the exact `sqlite_version` and `sqlite_vector_version` inputs; read its version and increment in Forecast and its channel in the pair section. The common instruction leaves `sqlite_comment`, `sqlite_vector_comment` and `misc_comment` empty unless the maintainer wants release-note paragraphs; there is no channel or distribution-version input. Existing candidates retain their individual run/PR links, states, attempts and preparation references, with no recommendation to start duplicates. A plan containing only existing candidates remains a complete nonempty plan. Manual Updates selection remains independent of Watch history; its existing rollback/comment rules still apply. See [candidate preparation](candidates.md).

To draft the optional comments from official upstream sources, use the [release-comments skill](../.42p/.agents/skills/release-comments/SKILL.md): `/release-comments sqlite_version: <version> sqlite_vector_version: <version>`. It resolves the published comparison reference and same-engine components, explicitly describes a first engine transition without inventing a numerical sqlite-vec-to-Vector changelog, accepts an explicit distribution baseline and returns one English line per nonempty field with source links outside the comments. The Summary links to the skill and the plan email recalls its invocation. Drafting remains separate from launching Updates.

## Schedule, manual planning and notifications

Watch is configured each Friday at 08:00 in `Europe/Paris`, including winter/summer time changes. GitHub may delay a scheduled execution. Open the [Watch workflow](https://github.com/at-rama/sqlite-vector-wasm/actions/workflows/watch.yml) and use **Run workflow** to recalculate a plan independently of the cron. Select the branch to inspect; there are no candidate-selection or version-override inputs. Manual Watch only reads, calculates and presents. Starting Updates is a subsequent, separate human action.

GitHub requires the Watch definition on the default branch before hosted manual dispatch is available. A development branch can then be selected under [GitHub's manual-run rules](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow). This condition does not authorize premature integration. PR checks run the offline suites; PR updates do not launch the live Watch.

Open an execution's **Summary** to read the Markdown plan without raw logs. A complete empty plan is a normal success. Discovery, publication/candidate state or calculation failures have an explicit failed-stage summary and an unsuccessful execution. Ignored `.work/watch/result.json` and the execution artifact retain available nonsecret diagnostics; neither becomes input to later selection.

After successful planning and preservation of its artifact, Watch consumes the result and sends a short plan email through Resend when the complete plan is nonempty. GitHub can additionally emit completion notifications according to your [Actions notification preferences](https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications), including for empty plans or failed runs. That account-controlled behavior is outside the project's email rule; this repository does not suppress it or change account settings.

GitHub can disable scheduled workflows after repository inactivity. Reactivate the workflow manually under its normal UI controls. Watch adds no keepalive, alternate scheduler or automatic reactivation. Disabling only its schedule leaves manual planning distinct; disabling the whole workflow disables both triggers.

## Plan email

Watch uses Resend → Gmail to send one short plan email for each successful planning execution with a complete nonempty plan. The message gives the pair count and links to the run; the Summary and artifacts remain the reference for details and diagnostics.

| Planning result | Project email |
| --- | --- |
| Successful, complete nonempty plan | One plan email, including when all entries already have preparation or a PR |
| Successful empty plan | None |
| Failed or incomplete planning | None |

Scheduled and manual triggers use the same rule. There is no trigger-specific filter, notification deduplication or sent-plan history; recurring proposals can appear in successive plan emails. This does not change Watch's current-candidate awareness or its prevention of duplicate preparation.

Configure the GitHub Actions secret `RESEND_API_KEY` and repository variables `RESEND_FROM` (the address on your dedicated, verified Resend sender domain) and `RESEND_TO` (the Gmail recipient). Only the email step receives this configuration. Empty or failed plans need no mail configuration and cause no send. The sender reads the current result; it does not discover versions, inspect candidates or calculate another plan.

Each eligible execution makes one request, without automatic retry, notification history or fallback message. Missing configuration, an unreadable result, provider rejection or a request failure makes the email step fail while preserving the producer's result and Summary. The logs omit the secret, addresses and provider response body. A successful step means Resend accepted the request; it does not establish Gmail receipt or an Android notification. A network or response failure may leave acceptance unknown. Manually rerunning an eligible execution can produce another fresh mail.

## Development checks

Run `node --test tools/watch/tests/*.test.mjs` for captured-source readers, synthetic publication/candidate fixtures, pure eligibility/forecasting, summary outcomes, event boundaries and plan-email behavior. `sh tools/test-repository.sh` registers these suites and fails if an implemented Watch or sender lacks a mandatory suite. Notification tests use an injected Resend transport and actual producer records at the sender CLI boundary. They cover both triggers, recurring plans, existing candidates, empty/error silence, request/configuration failures and secret-safe output. Tests perform no live Watch dispatch, email send, candidate preparation or publication.

The planning entry point is `sh tools/watch.sh`, with the native read-only Actions token and execution summary destination supplied by the workflow. The separate sender entry point is `node tools/watch/notify-cli.mjs`, run from the checkout root after successful planning and artifact preservation. It reads `.work/watch/result.json`, uses the current Actions run identity for the link and requires the three mail configuration names above only for a nonempty plan. Neither entry point needs a third-party runtime package installation. Actual manual execution remains separate from offline development checks and must respect GitHub's branch/dispatch availability rules.
