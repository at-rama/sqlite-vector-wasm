# Prepare a distribution candidate

After the preparation workflow is integrated on main, a maintainer starts **Updates** through GitHub Actions, selects `main`, and supplies:

| Field | Value |
| --- | --- |
| `sqlite_version` | Exact official SQLite version, for example `3.54.0` |
| `sqlite_vector_version` | Exact published SQLite-Vector version, for example `1.1.2` |
| `sqlite_comment` | Optional SQLite release-note paragraph |
| `sqlite_vector_comment` | Optional SQLite-Vector release-note paragraph |
| `misc_comment` | Optional miscellaneous release-note paragraph |

Selection does not depend on watch suggestions or intervening releases. There is no channel or distribution-version input. Nonempty comments are trimmed at their edges and joined in SQLite → SQLite-Vector → miscellaneous order with one blank line between them; the resulting single release comment is required for a rollback. Comments, including quotes, real newlines and shell metacharacters, remain JSON data. The existing resolver determines source admissibility: stable SQLite full-source releases and published SQLite-Vector stable/prerelease release/tag/commit archives with sufficient official integrity metadata. Development snapshots and unsupported selections fail. An established pin cannot silently acquire a new digest. Selecting the recorded pair preserves its source-lock bytes.

The workflow resolves and validates `inputs/sqlite-vector.sources.lock.json`, reconciles the selected upstream notice inputs, then introduces or updates `inputs/release.json` using A-release's existing schema:

```json
{
  "schemaVersion": 2,
  "sqlite": "3.54.0",
  "sqliteVector": "1.1.2",
  "releaseComment": "First distribution",
  "preparation": {
    "runId": 17,
    "url": "https://github.com/at-rama/sqlite-vector-wasm/actions/runs/17"
  }
}
```

Run 17 illustrates the format; the workflow writes its actual repository/run reference. The descriptor contains no reserved package version. Preparation commits the source lock, release descriptor, notice manifest, changed notice texts and documentation inputs together on `candidate/run-<runId>-<attempt>`, checks the clean repository snapshot and opens a qualification-pending PR. It does not compile the product, run browser acceptance or claim a qualified archive. Required repository tests and full product qualification run in that PR. A successful source preparation or fixture test alone is insufficient for integration.

Before candidate checks, preparation refreshes the two SQLite notices or the Vector Apache notice for the changed upstream in `tools/package/notices/` and their version/origin/digest records in `tools/package/notices.json`. SQLite notices come from the digest-verified full-source archive: `LICENSE.md` and the initial `/* @preserve` license block in `ext/wasm/api/sqlite3-license-version-header.js`, excluding subsequent version/template code. Missing or unsupported SQLite notice sources stop preparation. SQLite-Vector uses the required `LICENSE.md` from its verified commit-addressed archive, bound to the selected published release/tag/commit. Missing required content fails without a different source or license fallback. Its raw Apache text must satisfy the existing package provenance checks; unsupported normalization fails. Preparation validates the pinned FP16 license record and Git blob identities of the incorporated headers against the selected archive; dependency drift stops rather than adopting a new FP16 revision.

Preparation preserves wording and embedded runtime notices. Recorded text removes trailing horizontal whitespace and blank EOF lines and ends with one newline; refreshed records identify the raw source digest, extraction/normalization and shipped digest. Package/release checks still require exact version associations and byte hashes and never download notices. Unchanged groups, including Emscripten/toolchain notices, retain their recorded bytes/metadata. Same-pair reconstruction validates existing notices without new notice acquisition; absent historical raw digests or immutable origins are reported as not established rather than invented.

Notice acquisitions stay under `.work/updates/run-*/notice-inputs/`, separately from the fresh production workspace. `notices.json` in the run directory distinguishes refreshed source proof from retained-record validation; `notices.log` records the helper execution. Reconciliation failure stops before candidate commit, repository checks and remote writes. Available expected identities and diagnostics are retained even when failed acquisition removes its temporary sources. A successful reconciliation alone does not qualify a candidate.

The same candidate includes the canonical README and complete Usage guide shared by the site and package. Preparation sets `tools/site/docs-example.json` to explicit candidate/Vector mode, records all authored source digests, and leaves version/status rendering to the qualified archive. It introduces no forecast literal into those sources. Missing documents stop preparation. After the PR opens, Acceptance produces one exact-head archive through all mandatory production/browser checks. Its dependent Site jobs consume that same artifact and execute the existing real-browser example once in the main context and module Worker; head, composition, source hashes and archive identity must agree before integration. Generated examples and archives remain temporary.

The PR links the shared unpublished documentation preview and exact-head checks. Its initial readiness is **qualification pending**. Approve any native-token workflow runs awaiting human approval, inspect the required acceptance result including Site build/deploy for that head and archive, and verify the preview's displayed revision before deciding to merge. A shared URL can be replaced by another PR; missing, failed, stale or mismatched mandatory checks leave this candidate ineligible. Release rechecks applicability after human integration.

The actual Git/npm state determines the forecast. A stable first candidate forecasts `0.1.0` on `latest`; later experimental inputs use the shared `next` policy. Initial experimental publication remains prohibited. Unavailable or inconsistent history and identity collisions stop preparation. The preparation forecast is explicitly provisional. The PR producer recalculates against its observed state and records the qualified archive/identity; Release recalculates again for the integrated definitive payload. No identity is reserved.

The run retains `updates-<runId>-<attempt>` for 30 days from `.work/updates/`. `candidate.json` records the invocation, base/prepared commits, source/notice/document controls, state observation, provisional forecast and branch/PR outcomes. Resolver/notices/repository logs distinguish refreshed proof from retained input validation. No prepared archive, browser pass or publication provenance is claimed by this run; those belong to the PR producer and definitive Release. Generated files remain ignored and outside candidate commits.

Failed runs retain available evidence. An operation marked failed was unsuccessful; an unknown write requires inspection, and absent later operations did not execute. Preparation failure creates no completed candidate PR; a subsequent qualification failure leaves the already opened PR ineligible. A push or PR transport failure can leave a remote branch: inspect it rather than treating the run as complete. An empty expected-ref lease enforces atomic branch creation and refuses every existing ref, including races; it never authorizes replacing a candidate. There is no destructive cleanup or alternate-identity retry. Before source resolution or qualification, preparation reuses Watch’s read-only current-candidate inventory. An existing PR or other active preparation for the exact pair is referenced in `candidate.json` without rebuilding, creating another branch or asserting integration eligibility. The current run/attempt is excluded from that observation. Other pairs remain independent. This is an observed snapshot, not a reservation or transactional lock; concurrent inventory races can stop or duplicate work and require inspection. Existing branches are never replaced. An inaccessible inventory is a failure, not an empty candidate set.

Enable **Allow GitHub Actions to create and approve pull requests** in repository Actions settings and grant the native job token `contents: write` and `pull-requests: write`. Checkout credentials are not persisted; push authorization is scoped to process environment and excluded from retained diagnostics. No permanent token, npm credential or publishing OIDC permission is used. If repository policy rejects the native token, preparation reports failure without a credential fallback.

GitHub documents [native token behavior](https://docs.github.com/en/actions/concepts/security/github_token): PR workflows opened or updated by the native token can await human approval. Approve pending workflow runs, inspect their results, review the candidate head/descriptor, then decide whether to merge. The implementation's read-only PR rehearsal does not demonstrate live PR-creation permissions. Its source-preparation rehearsal uses the recorded pair and creates neither remote branches nor PRs; it is not a product qualification.

Preparation stops at the PR. It cannot merge, enable auto-merge, create release tags or publish GitHub/npm distributions. Edits or rebases invalidate the earlier evidence's applicability to the new revision. Human integration triggers [A-release](publication.md), which recalculates and qualifies the definitive main revision and exact payload. Follow [First npm publication](bootstrap.md) to establish initial access before candidate integration and complete the exact-archive npm handoff afterward.

The fixed product is SQLite-Vector. Legacy sqlite-vec fields, mixed inputs and engine selectors are rejected. The handoff supplies exact Vector/run/commit/PR identities; Watch reads current Vector titles and schema-2 descriptors against each candidate head's recorded Vector lock, retaining distinct run attempts and PR identities. Manual preparation remains independent of that consumer and its discovery baseline.

Published alpha/beta/rc inputs are conditionally admissible with exact official non-draft release/tag/source binding. As observed on 2026-10-19, no such Vector prerelease was published in the inspected official releases or npm versions; branch headers, artifacts and aliases do not establish a release. Synthetic prerelease tests demonstrate classification, not an actual alpha build. The product retains `latest`/`next` and its own alpha series. First transition from the historical 0.x sqlite-vec product consumes A-release's MINOR rule; incomparable engine version numbers are never ordered. Only an older comparable component requires a rollback comment.

`sh tools/updates.sh rehearsal` exercises source preparation for a same-repository implementation PR using the recorded Vector pair and actual run/attempt. It requires a clean dedicated checkout and source-preparation prerequisites, and permits a local temporary branch/commit without a remote write adapter or publisher. It reports `prepared-without-pr`, not a qualified archive. The tooling PR's Acceptance producer separately runs the complete product/browser path on its own exact head, with any fixture forecast explicitly labelled. Neither source preparation nor fixture policy state establishes live publication authorization.

Preparation retains exact selected sources/notices/document hashes, comment, run/attempt, commit and available diagnostics under `.work/updates/`. The PR run retains `candidate-<run-id>-<attempt>` and `site-checks-<run-id>` for review, including the complete qualified archive and separate example/assembled-site results. These short-lived handoffs are not durable delivery authority. Renew unavailable proof before integration; Release stops if mandatory review proof is inaccessible. A completed publication retains its manifest, archive, attestation and delivery receipt in the existing Release, so stable Site redeployment needs no expiring CI artifact.

On a push or PR transport timeout, inspect the existing branch/PR for the exact prepared commit before doing anything else; an uncertain write is not a proven rejection. An acknowledged push followed by a local journal failure is reported separately and no later PR write is attempted. An explicit API rejection remains a failure. Do not overwrite a branch, select a fresh identity to hide a partial result, or add automatic replay. Resolve the identified missing operation manually, preserving the prepared selection/commit and human review boundary.
