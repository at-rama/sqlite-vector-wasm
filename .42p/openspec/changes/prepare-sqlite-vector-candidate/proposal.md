# Proposal

## Why

The adopted product engine is SQLite-Vector and A-release now consumes its exact schema-2 descriptor and recorded lock, but Updates still prepares sqlite-vec candidates. A-updates must connect the existing Vector input/build/package/acceptance path to human-selected, fully qualified candidate PRs without changing the publication policy or claiming an upstream alpha exists.

## What Changes

- **BREAKING**: replace the current Updates sqlite-vec selection/comment fields and candidate presentation with SQLite-Vector; keep exact manual selection, ordered comment aggregation and the qualified-PR stopping point.
- Resolve the exact official published pair through the existing Vector resolver, freeze the recorded Vector lock, schema-2 release descriptor and coherent notices before checking the clean candidate commit.
- Refresh SQLite and Vector license provenance for changed sources and validate the pinned FP16 dependency; retain unchanged valid records honestly. Do not relabel old notice bytes without establishing the selected release association.
- Consume A-release's existing component references, transition/alpha calculation and explicit-Vector definitive qualification. Keep prereleases conditional on an actual published, non-draft official release, with sufficient source/integrity metadata; branch snapshots, npm aliases and invented alphas remain excluded.
- Preserve exact commit/payload/run evidence, failures and create-only candidate presentation; adapt the nonpublishing preparation rehearsal, its workflow guard and preparation documentation. Remove current-pin coupling from the release test fixtures only where necessary for legitimate candidate updates.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `distribution-candidates`: fixed Vector dispatch, source/notice snapshot, shared forecast, exact qualification, schema-2 descriptor and candidate provenance/presentation.
