## Goals / Non-Goals

Realize this unit's changed obligations while retaining its complete existing effective contract. Bind the reviewed candidate documentation to the definitive qualified archive and identity; renew affected document/example checks before publication; provide complete matching GitHub/npm publication outcome to Site without making site deployment a publisher. No change to general 42P, source locks, human authority, published history, product channel/version policy, runtime API or unrelated unit is proposed.

## Decisions

Extend existing qualification/publication evidence with the minimum reviewed-document context needed to bind source head, authoritative merge revision, final identity and archive. Render mechanical final identity/status from qualified inputs; if bytes/number change, reassemble and rerun required acceptance/example/link checks. Refuse substantive unreviewed documentation changes. Only a complete matching publication result permits Site stable promotion. Preserve partial outcome diagnostics and bounded initial npm-pending semantics. Reuse publication evidence/artifacts, not a new release state registry or reservation mechanism.

The synchronized `distribution-release` baseline at main `741b26df750b3c1f0f5a00c1dd1e579b4e7c6d9e` plus this delta forms the effective contract; omitted unchanged requirements are retained, not deferred. Implementation tasks preserve that complete surface and checks; prior historical passes are not future acceptance evidence.

Public Markdown sources must remain readable on GitHub. Keep durable prose free of forecast-dependent literals where possible; any final-identity rendering is limited to reviewed mechanical fields. If a changed definitive identity would invalidate authored instructions or require substantive source edits, stop before publication and prepare a refreshed reviewable candidate rather than planning a post-publication documentation fix. No workflow writes directly to main.

## Risks / Trade-offs

GitHub success with npm failure is partial, never sufficient for stable docs promotion. A nominal workflow success or mutable branch tip alone cannot prove matching publication. Publication retry/collision rules remain unchanged.

## Migration Plan

After candidate/package/docs changes. Provides publication identity/outcome to publish-site-after-distribution. Site deploy failure after successful distribution publication is separately reported and does not republish or retag the product. Stage implementation/verification so each unit remains reviewable; the first five changes must be integrated coherently before a real candidate uses the new workflow. The demo has only the explicitly stated published-runtime dependency. Preserve previous public deployment on publication failure; do not roll back a published identity or fabricate a replacement artifact.
