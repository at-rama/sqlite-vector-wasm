# Release comments

Read `AGENTS.md`, the editorial standard and [candidate preparation](../../../../docs/candidates.md). Use the GitHub plugin for repository reads. Keep this an on-demand drafting aid; do not edit files, dispatch Updates or publish anything.

Accept exact `sqlite_version` and `sqlite_vector_version` values and an optional distribution reference. Example: `/release-comments sqlite_version: 3.54.0 sqlite_vector_version: 1.1.2`.

1. Resolve the published baseline, exact engine identity and embedded upstream versions from publication provenance. Use the current A-release `componentReferences` policy for each component: SQLite uses the channel HEAD or latest; Vector uses that channel’s Vector composition, otherwise latest if Vector, otherwise no numerical Vector reference. For an explicit distribution baseline, honor that exact composition and compare only components from the same engine lineage. Honor an explicit distribution reference; otherwise use the selected pair's channel HEAD (`latest` for stable pairs, `next` for experimental pairs, falling back to `latest` when no `next` exists). Follow the current publication reader and records rather than assuming tag names or versions. Do not treat repository pins, a Watch forecast or an unpublished candidate as a published baseline. State the reference and component transitions. If the baseline cannot be established, report that limit rather than inventing a comparison.
2. Read official upstream release notes for the selected versions and relevant intervening releases: SQLite's release logs and SQLite-Vector's [published GitHub Releases](https://github.com/sqliteai/sqlite-vector/releases), supplemented by exact-tag history or linked upstream fixes when needed. Summarize the cumulative difference only when a same-engine baseline exists. If none exists, explicitly describe the first engine transition and selected Vector release using its official notes, without fabricating a cumulative numerical sqlite-vec-to-Vector changelog. The discovery floor is not a published baseline; distinguish prereleases and rollbacks. Report missing or ambiguous evidence without guessing.
3. Draft one concise English line per nonempty field, prioritizing user-visible changes relevant to the distributed library. Preserve important compatibility restrictions and conditions. Exclude CLI-only, platform-only or optional-extension changes unless their applicability to this distribution is established. Do not turn an upstream benchmark into a performance claim for this WebAssembly build or imply qualification from release notes.
4. Leave an unchanged component's field empty by default. Allow a useful contextual reminder, particularly for a first release with detailed comments or an explicit request, but say that the version is unchanged and attribute the behavior to that version. Never present an already included fix as newly delivered. Leave `misc_comment` empty unless a separate, evidenced distribution change warrants it; upstream sources alone do not establish local changes.
5. Return `sqlite_comment`, `sqlite_vector_comment` and `misc_comment`, explicitly marking empty fields as empty. Put each nonempty line in a separate copyable block without the field label or source citations inside it. Give official source links and any material evidence limits outside the comments. Keep the comments optional and ready for human review; drafting does not initiate preparation or authorize publication.
