# Editorial standard

Applies to all human-facing repository prose. These rules govern presentation; [repository authority rules](../../AGENTS.md) identify the human-instituted Captures as the current design reference and distinguish them from derived projections and the [technical canon](software.md) owns engineering rules.

1. **Write for the reader.** Product documentation must directly explain the repository's purpose, intended capabilities, boundaries and consumption. Development content must explain what contributors need to work here. Internal engineering documents may use the precise vocabulary needed for their subject.
2. **Keep internal language in context.** Do not expose contracts, 42P terminology, agent instructions, verification mechanics or implementation workflows in product prose unless they help the reader use the product. Put relevant contributor commands and factual disclosures about agentic development in development content; link to deeper engineering material instead of explaining its machinery in the README.
3. **State the behavior directly.** Prefer what the project does or aims to provide over attribution such as “the contract requires”, “the specification says” or “the workflow ensures”. Do not present public explanations as internal obligations or approval criteria.
4. **Keep durable pages durable and factual.** Describe enduring goals without claiming a particular release, package, command or artifact exists without evidence. Use publication records for available versions. Do not narrate implementation progress or maintain requirement checklists in the README; mention transient state only when it materially affects use or development.
5. **Preserve meaning.** Editorial changes must retain scope, conditions, uncertainty, normative strength and source relationships. Do not turn intended behavior into evidence of implementation, or rewrite recorded engineering evidence as current status.
6. **Use established names consistently.** Preserve public spelling and case: SQLite, sqlite-vec, sqlite-vector-wasm, Node.js, npm, FTS5, Worker1 and OPFS. Do not invent synonyms or process labels for these concepts.
7. **Use code formatting for literals.** Use inline code for commands, paths, filenames, package identifiers in dependency/installation contexts, APIs, SQL identifiers and source handles; use fenced blocks for executable examples. Project and technology names in ordinary prose use plain text, without code formatting or quotation marks. Keep link labels readable plain text and preserve exact literal spelling in link targets.
8. **Keep documentation lean and connected.** Add only sections that help the intended reader. Link to existing requirements, engineering notes and development rules rather than duplicating them. Repository links must resolve, including local anchors. Do not add status dashboards, generic governance prose or placeholder sections.
